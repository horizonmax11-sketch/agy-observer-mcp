# 三方协作：独立判断，再共同完善一份方案

GPT、Gemini、Claude 都可提出问题、替代解释、证据、反例和修正。关注角度随任务轮换；不固定某一模型只能创新、执行或审核，也不按多数票决定事实。

Gemini 和 Claude 分别通过配置的 Antigravity 模型调用。GPT 由 MCP 客户端提交公开发言；本服务不另行调用 GPT API，也不认证客户端所声明的模型身份。要取得三份独立初判，客户端必须在只含原始材料的新 GPT 请求中取得其发言，不能将已看过历史的回答标为独立盲评。

## 怎么交流

像几位同事一起把事情做好：接住具体想法，简短说出看法、原因和下一步，每轮通常两到四句，只推进一两个点。可以直接提不同意见，也可以改口。减少审阅式评判、反复辩解和机械地宣读规则。

| 情况 | 更自然的说法 |
| --- | --- |
| 自己理解错了 | “我刚才把额度独立理解成额度大小不同了，这里改一下。” |
| 还缺信息 | “这里还需要看一下实际用量，我们先查这一项。” |
| 想走另一条路 | “我更倾向先做个小实验，比较省事，也能看出差别。” |
| 接住别人的补充 | “这个停止点加得好，我把它放进方案，再把没解决的问题单独列出来。” |

不确定之处应落到具体缺口和核实办法上。观点随理由和证据调整，避免为了客套连续赞同，或为了显得独立刻意反对。`message` 写给讨论参与者；引用、依据、调整原因和来源交给结构化字段，在页面的“依据与记录”中展开查看，正文无需重复。

这份约定同样适用于客户端提交的 GPT 发言。新提示词影响后续请求；既有真实讨论保留当时原文，离线演示用于展示交流方式，不能作为模型表现的验收证据。

## 一次任务的过程

1. 用 `agy_council_create` 创建目标、原始事实和每个外部模型的次数预算，默认各两次。材料应区分用户偏好、已知事实和待验证假设，避免把协调者的方案写成既定事实。
2. 获取 GPT 的简短独立初判，以 `agy_council_note(kind="initial", initial_context="fresh")` 提交。`fresh` 是客户端声明；已看过历史应使用 `history_visible`，不确定使用 `unknown`。
3. 调用 `agy_council_round`。默认同时调用 Gemini 与 Claude，各一次；首轮只发送原始目标、事实和相同的中性问题，不发送其他参与者的发言。也可显式指定其中一位；先完成者的回答仍不会带入另一位的初判。
4. 三份初判成功后用 `agy_council_reveal` 一起公开。失败不会自动重试或退款；尚未完成也可提交 `summary` 归档，保持首轮封存。是否再次调用由客户端明确决定，仍受原预算限制。
5. 公开后围绕具体问题增量讨论。可记录 `observation`、`question`、`challenge`、`evidence`、`revision`、`support`、`pass`。改变立场必须引用原发言并说明原因；支持需要引用和依据。依据仍需核验，填写字段不构成事实验证。
6. 以 `kind="plan"` 汇集一份共同方案草案，注明 `references` 和 `expected_plan_version`。首版传 `0`；后续修改传读取到的版本并填写 `change_reason`。旧版本仍保留；版本不匹配时拒绝覆盖。协调客户端负责保存草案，任何参与者都可提出修改或异议。
7. 按问题选择一位或两位参与者继续，不要求每轮全员发言。并发批次从同一份调用前快照生成提示词；需要接住刚返回的意见时，显式发起后续话轮。没有新增信息可以 `pass`，不会自动触发下一轮。
8. 用 `summary` 记录阶段结果、待验证项及保留分歧。归档不表示三方同意；问题被回答也不表示答案被认可。不自动生成“全员共识”标签。

## 按项目分工写提示词

新项目推荐先传入`project`简报，三方理解并公开后再调用`agy_council_assign_roles`选择角色、生成提示词；同任务内可按阶段调整并保留历史。见[项目理解与动态分工](project-workflow.md)。以下`roles`方式用于兼容已有、预先确定职责的任务。

创建时可传 `roles`，包含 `gpt`、`gemini`、`claude` 三项，每项最多600个UTF-16单位。分工**在首轮公开后启用**，首轮仍使用相同原始材料和中性问题，避免角色先限定判断。未传时继续使用通用协作约定。

例如，改进一个本地MCP项目时：

```json
{
  "goal": "改进本地MCP的讨论体验和可靠性",
  "facts": "填写原始需求、已知行为和可核对材料，不夹带预定结论。",
  "max_turns_per_model": 2,
  "roles": {
    "gpt": "核对实现与验证：追踪代码行为、依赖和迁移成本，提出小步可检验改动；更好的替代方案出现时调整。",
    "gemini": "检查实际使用过程：沿创建、阅读、继续讨论与查看结果寻找具体卡点，给出可复现步骤、可观察现象和验证办法。",
    "claude": "寻找遗漏与替代路径：用具体反例检查共同前提和角色盲区，说明替代做法的适用条件。"
  }
}
```

提示词写清当前问题、优先关注点和可用的检查办法，不预设必须支持或反对谁。公开后每位远端模型只收到自己的项目分工，并附带共同约定：允许跨角色补充，没有新增内容可以pass，分工不赋予最终裁决权。客户端应读取GPT分工并应用于后续GPT发言；服务不会另外调用GPT。页面“项目分工”可查看原文。

使用上述旧式`roles`创建的任务，分工创建后保持不变；需要动态调整时使用新的`project`流程。把不同关注点分给谁，应随项目需要调整，不把模型品牌等同于固定能力。是否更有效仍应通过同任务、同预算对照验证。

## MCP 工具

| 工具 | 用途 | 模型请求 |
| --- | --- | --- |
| `agy_council_create(goal, facts="", max_turns_per_model=2, roles=null, project=null)` | 新建任务；新项目传project，旧方式可传roles，两者互斥 | 无 |
| `agy_council_assign_roles(...)` | 理解后选角并生成提示词，或追加本阶段分工版本 | 无 |
| `agy_council_note(...)` | 提交客户端发言或共同方案版本 | 无 |
| `agy_council_round(discussion_id, participants=null, focus="", reply_to=null)` | 默认 Gemini/Claude 各一次并发；也可只选一位 | 最多两次 |
| `agy_council_reveal(discussion_id)` | 收齐后公开首轮，进入讨论 | 无 |
| `agy_discussion_read(discussion_id)` | 读取三方任务；省略编号列摘要 | 无 |
| `agy_discussion_recover(discussion_id)` | 从已关联运行恢复中断终态；不重发 | 无 |

`participants` 使用 `"gemini"`、`"claude"`。首轮禁止 `focus` 和 `reply_to`，防止临时塞入引导性意见。后续可以用 `focus` 指定证据缺口或要求反查共同前提。模型通过 `references` 引用看到的发言、通过 `answers_to` 显式回应别人的问题；不能引用同批次尚未出现的结果。

三方调用使用CLI的 `--json-schema` 约束终态格式（需CLI支持，已实测1.4.7）。正文有效时，各项元数据独立检查；无效引用被丢弃并提示，不影响正文或其他有效字段。缺少修正理由/支持依据时按普通补充记录。无法解析的JSON保留原文，不猜补引号或推断问题；CLI重复输出两份完整且内容相同的JSON时可读取一份，内容不同时保留原文。原始运行记录始终保留。`agy_discussion_recover` 可用改进后的解析重新提取成功降级记录，不重新调用模型。

`agy_council_round` 返回 `discussion_url`，自动开窗也带当前任务编号；复制页面地址即可直达这场讨论。编号不存在或被离线筛选隐藏时，页面明确提示，不切到另一场冒充结果。链接依赖本地服务仍在运行，不是公网地址。

共同草案示例（编号应取自实际任务）：

```json
{
  "discussion_id": "task-id",
  "kind": "plan",
  "content": "根据讨论整理的执行步骤、验收条件和未决问题。",
  "references": [1, 2, 3],
  "expected_plan_version": 0
}
```

## 上下文、并发与额度

讨论阶段保留成功初判、最新方案、最近六条消息、明确引用及最多三个待答问题；内容按字段限长，带入、截断与省略编号可查，原文不会因省略而删除。共享讨论使用GPT、Gemini、Claude名称，与页面一致，避免回复中出现难以辨认的A/B/C；首轮不带其他模型的名称和意见。界面保留实际请求来源与运行编号，便于核对。

同一实例最多并发两个不同的配置模型，不允许同模型重叠运行；新的批次必须等当前批次结束。单方失败或取消不自动取消另一方成功结果；取消整个批次则请求清理双方。失败、取消和超时也占各自尝试次数。独立次数预算不等于实时读取或保证服务商额度，也不是跨 MCP 实例的全局限额。

首轮“封存”是防止对话 API、界面和后续初判提示词意外泄露的工作流程，不是本机访问控制。操作者仍可通过 `agy_status` 或磁盘读取原始运行。CLI 不使用续聊参数，但本项目不能证明提供商内部无共享状态；不声称三个模型在统计意义上完全独立。

## 如何判断有没有改善

评估应固定任务、事实、模型设置和总调用预算，对比直接轮流讨论与隔离首轮的流程。检查错误的首观点是否被纠正、交换顺序后的差异、是否出现有依据且影响决策的新增内容，以及总 token/延迟。对“没有新增信息”的判断需要人工核查，不能用发言长度或反对次数替代。上线链路验收只证明机制可运行，不能证明质量优于单模型或已经消除迎合。

离线预览不调用任何模型：

```sh
python -m agy_observer.demo --council --state-dir ./state --port 8766 --open
```

旧双方协议仍可使用，见 [双方协作](collaboration.md)。
