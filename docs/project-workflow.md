# 先理解项目，再选择本阶段需要的三个角色

0.8.0可选择2–4位参与者（包含客户端gpt），claude可走Antigravity/Claude Code，codex表示独立CLI；下面三方例子是兼容默认。分工、收齐与公开条件适用于本任务全部所选参与者，详见[多渠道接入](channels.md)。


不同项目、同一项目的不同阶段，可能需要完全不同的分工。先确认要解决什么，再选择角色和承担者；GPT、Gemini、Claude都可以换角色，也可以质疑分工本身。

## 1. 客户端先读取材料

让使用MCP的客户端阅读与当前目标有关的README、代码入口、测试、任务说明和运行记录。只整理必要内容：目标、阶段、成功标准、约束、材料缺口，并写明材料来源和具体观察。没有读到的文件应列为缺口，不宣称已经检查。

本MCP不读取任意项目路径。`materials`是客户端提供的文字材料，不是让服务打开文件的路径参数；文件名本身不足以替代内容。网页和模型输出中的建议也不能替代已核对事实。

客户端可以先在聊天中展示准备提交的五项简报，用户可直接纠正；信息已充分且用户授权继续时不必额外停下来确认。创建后，本地页面的“项目理解与材料”可展开查看。页面本身只读，不提供编辑或确认按钮；需要纠正材料时，在聊天中告诉客户端，由其更新后续阶段的`project_updates`。原始简报仍保留，发现根本目标错误应归档并新建任务。

## 2. 创建项目理解任务

调用`agy_council_create`，传入`project`，不要同时预设`roles`。五个字段均需填写；不确定可以如实写“待确认”，整体JSON最多3000个UTF-16单位。

```json
{
  "goal": "让首次使用者按文档完成一次调用，并能定位结果",
  "max_turns_per_model": 3,
  "project": {
    "stage": "已有原型，准备首次发布",
    "materials": "客户端已读README安装段、入口模块和运行记录：目前只有启动命令，缺少首次成功调用的示例。",
    "success_criteria": "按文档在干净环境完成一次调用，找到对应记录；失败原因可定位。",
    "constraints": "保留现有接口；不引入新的运行依赖；本轮每个外部模型最多三次，不自动重试。",
    "unknowns": "首次失败发生在配置、登录还是记录查找？干净环境尚未验证。"
  }
}
```

次数预算包括理解与后续推进，默认仍各两次；三次只是本例的预算。不要为了走完流程偷偷加次数。

创建后的示例状态是`workflow_stage="understand"`、`role_version=0`。三份理解公开后为`assign`；首次选角后为`work`、`role_version=1`。这些表示流程位置，不是用户已点击确认或模型已全体认可。

## 3. 三方各自理解，再共同确认重点

GPT先用只含原始材料的新上下文形成简短理解，以`agy_council_note(kind="initial")`提交；如已看历史，应如实填写`initial_context`。Gemini、Claude用`agy_council_round`取得独立理解。首轮不发送其他人的意见或角色提示词，不要求各写一份完整方案。

收齐后用`agy_council_reveal`一起公开。接着澄清目标、成功条件与遗漏，保留具体分歧。必要时可在尚未选角时继续话轮，但会占原预算。目标、发布权限、成本等取舍需要用户决定时向用户确认；可逆实现细节可列明假设并验证，不必为每处分歧停下来。

“三份理解已公开”表示材料已经可互相检查，不自动表示三方认可。首次分工必须引用三方初判，让选择有来源；引用不是投票或授权。

## 4. 先选角色，再决定由谁承担

客户端根据三方发现的主要缺口，选出当前最需要的三个互补角色，再分配给模型。不要默认某个品牌只能创新、实施或审核，也不要把“主提—附和—挑错”当成项目分工。

每个角色填写：

| 字段 | 内容 | 长度上限（UTF-16单位） |
| --- | --- | --- |
| `role` | 角色名称，三位需不同 | 80 |
| `focus` | 当前优先解决的具体问题 | 200 |
| `output` | 有发现时带来的产出和检查办法 | 200 |
| `reason` | 为什么这个阶段需要此角色、为何这样分配 | 300 |

调用`agy_council_assign_roles`，例如先前材料和初判发现“成功定义不清、安装路径未验证、失败无证据”时，可以选择：

```json
{
  "discussion_id": "实际任务编号",
  "stage": "首次使用流程验证",
  "rationale": "从三方初判中选出成功定义、操作路径、失败证据三个缺口；本次由GPT澄清边界，Claude验证路径，Gemini设计证据检查。仍保留干净环境尚未实测这一问题。",
  "references": [1, 2, 3],
  "expected_role_version": 0,
  "assignments": {
    "gpt": {
      "role": "成功条件澄清",
      "focus": "把首次成功调用和找到结果写成可检查的条件。",
      "output": "给出可观察现象、范围及需要用户决定的取舍。",
      "reason": "当前成功标准模糊，先减少目标歧义；本次承担此缺口。"
    },
    "claude": {
      "role": "安装路径验证",
      "focus": "沿文档步骤追踪依赖、配置和首次调用的断点。",
      "output": "具体步骤、失败现象与最小修复；尚未实测的步骤单列。",
      "reason": "初判发现干净环境没有验收，必须检查真实操作路径。"
    },
    "gemini": {
      "role": "失败证据设计",
      "focus": "检查失败能否区分配置、登录与调用问题。",
      "output": "可复现用例和判断依据，避免只靠一条成功记录。",
      "reason": "现有材料无法解释失败，需要能核对的证据。"
    }
  }
}
```

服务从结构化分工生成三份角色提示词，保存在`roles`中。每份含职责、产出及跨角色补充/质疑、没有新发现可pass的约定。远端话轮自动带入当前项目简报和自己的提示词；客户端读取GPT提示词用于后续GPT发言。选角本身不调用模型，不自动增加预算。

这些是本项目本阶段的选择，不是可直接套用到所有项目的固定模板。只校验名称和结构，角色是否真正互补仍需参与者检查。

## 5. 围绕一份方案推进

选角后再讨论具体方案，以`agy_council_note(kind="plan")`记录共享草案。围绕前面的具体问题补证、提出反例、修正或pass，不要求每轮三人都交完整报告。可通过`participants`只找相关的一位；并发用于同一快照，需要接住刚返回的意见时使用后续话轮。

## 6. 阶段变了，再调整分工

当项目进入实施、发布或出现新的主要风险，再调用同一个`agy_council_assign_roles`。传当前`expected_role_version`、新分工、阶段、调整原因及新的发言引用；可通过`project_updates`更新简报的已知内容、约束、成功标准或待查项。最多8版，仍受40条消息和原调用预算限制。

分工调整会追加版本和一条时间线记录，旧提示词、旧简报与旧发言保留。每条新发言记录当时的分工版本。过期版本、仍有运行中的话轮、已归档任务会拒绝修改；修改分工不会恢复或扩充模型次数。

页面展示理解/选角/推进阶段、项目材料、当前三份分工及历史调整。当前阶段不等于任务已完成；归档仍保留未决问题。

## 判断是否值得继续使用

用相同项目、材料和总预算比较固定分工与按项目选角，查看遗漏是否减少、是否形成有依据的新发现、方案是否因此改变，以及花费和延迟。不要用角色数量、发言长度或相互支持次数代替效果评估。
