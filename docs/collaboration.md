# 协作机制与约束

## 为什么增加协作任务

原来的 `agy_run` 只有独立问答，分工、反馈和决定由外部维护者手动拼接。协作任务把目标、职责、消息引用、决定与模型调用归入同一份本地记录。

主维护者由调用端承担，审阅者由当前配置的CLI模型承担。每次请求仍只调用一个模型，不会后台启动另一份Codex或多个Gemini代理。主维护者的身份是客户端声明，未经本服务认证。职责提示也不构成技术权限隔离。

## 消息约定

- `proposal`：主维护者提交可审阅方案与材料。
- `review`：服务为显式模型尝试创建，关联实际运行编号；客户端笔记不能指定此类型。
- `feedback`：主维护者反馈；用 `reply_to` 指向已有消息。
- `decision`：主维护者记录取舍；必须有引用、理由和 `accepted` / `rejected` / `deferred`。可以分别对同一条审阅中的多条建议记录决定。
- `summary`：主维护者总结并关闭任务。关闭后保留只读，后续新目标创建新任务。

不会自动判断“达成共识”，模型返回成功也不会自动设置任务完成。方案实现和测试结果须由主维护者明确说明；服务不认证这些声明。

## 上下文与限额

目标最多2000 UTF-16单位，双方职责各500，主维护者单条笔记4000，本轮要求2000。每个任务最多40条消息、1–8次模型尝试（默认4次）。建议在消息上限前提交总结。

下一轮优先包含指定引用、最近3条决定和最近6条消息，每条内容最多800 UTF-16单位，并列出带入、截断与省略的消息编号。超过总提示16000单位时明确拒绝，不隐式放宽。模型缺少的信息应由主维护者在新笔记中补充。

任务内审阅回复最多保存8000 UTF-16单位，超出会明确标为摘录；完整回复仍在关联的 `status.json`，可用 `agy_status` 获取。任务单文件读写上限2 MiB；页面列表缓存轻量摘要。

## 调用、取消与恢复

创建、写笔记、读取和恢复均不调用模型。只有 `agy_discussion_turn` 发起一次模型尝试，执行开关、单个活动调用、超时及输出限额沿用原运行器。未开启执行时不占用次数；保留尝试后，即使失败、取消或未成功启动CLI，也不退回次数。

运行中拒绝对同一任务追加笔记或再次审阅，防止审阅依据悄悄改变。可以在单次调用视图或 `agy_history` 获取活动 `run_id`，用 `agy_cancel` 取消。正常终止记录终态；跨进程中断后调用 `agy_discussion_recover` 对齐已有终态。仍活动或尚无终态的关联运行会被拒绝恢复。此时应先检查/停止原进程；恢复不会猜测进程已退出、重发请求或归还额度。

读写使用短临界区与独占 `write.lock`，不在模型等待期间持有文件锁。若进程在写入期间崩溃，残留锁会阻止后续写入；操作方确认没有写入者后可移除该锁。读请求不删除锁、不执行自动修复。一个状态目录建议由一个MCP实例管理；执行并发限制是实例级的，不是跨实例的全局计费锁。

## 存储与隐私

`<state>/discussions/<discussion_id>.json` 保存任务；`<state>/runs/<run_id>/` 保存调用，二者用编号关联。两类数据均明文、仅在本地；不要提交GitHub。HTTP仍仅为loopback只读查看器，无执行和写入路由。磁盘数据不自动过期。

0.3不修改已有真实历史，也不把过去的独立问答自动归入一场协作。离线演示明确标为模拟，不能视为真实多轮验收。
