# 持续项目：记忆跨讨论保留，按需要继续协作

0.9.0增加独立的项目档案。项目寿命由实际工作进度决定，不由固定轮数决定：可以暂停、重开客户端、更换讨论主题，再接着原来的事实、方案和各自观点推进，直到明确完成项目。

这是 MCP 保存并重新提供的公开项目上下文，不是声称模型永久记住所有内容，也不使用原生 CLI 的 resume 参数。Antigravity、Claude Code、Codex CLI 共用相同机制；客户端 GPT 和独立 Codex CLI 仍分别标记。没有迁移认证、复用登录文件或自动发起模型请求。

## 三种记录各司其职

| 记录 | 内容 | 如何继续 |
| --- | --- | --- |
| 项目档案 | 有来源的事实、分歧、各方观点与理由、行动项、完整当前方案和状态 | 跨讨论、跨客户端会话保留，每次更新追加检查点 |
| 各自观点轨迹 | 每位参与者的公开发言、理由、改变判断的原因、渠道、请求模型及运行编号 | `agy_project_read(participant=...)` 查看，按来源取回原文 |
| 单场讨论 | 当前话题、角色及调整版本、消息引用、问题和实际调用 | 可继续原讨论，也可新建话题后显式关联同一项目 |

项目档案是客户端有来源的工作记录，不代表全员认同或外部核验。模型可以质疑旧前提；不同意见和改口原因不能为了形成摘要而抹掉。旧发言不会被改写成新的外部调用结果。

## 首次建立项目

先用 `agy_project_update` 建立档案，不调用模型：

```json
{
  "project_id": "demo-project",
  "expected_version": 0,
  "name": "示例项目",
  "goal": "完成实现和可复核的验证",
  "reason": "建立持续协作记录"
}
```

随后正常创建双方或多方讨论，再关联项目。已存在的本地讨论也可以关联：

```json
{
  "project_id": "demo-project",
  "discussion_id": "实际讨论编号",
  "expected_version": 1,
  "reason": "本场讨论属于该项目，按需持续推进",
  "on_demand": true
}
```

以上参数传给 `agy_project_link`。`expected_version` 必须使用项目的当前版本；关联时可能同时保存旧讨论已有的记忆和方案，务必以返回版本或再次读取的版本为准。

默认 `on_demand=true`：取消这场讨论的固定总调用次数和消息条数上限，次数成为累计用量记录。每次请求仍由客户端显式调用，服务不会启动循环、自动重试、自动选择其他渠道或放宽 CLI 审批。超时、输出上限、并发最多两位、取消和客户端审批继续生效。`on_demand=false` 可显式保留原来的次数预算。

关联是明确的项目归属，一场讨论不能悄悄改绑到另一项目；不同项目的资料不会自动混用。档案与讨论均存放在当前 MCP 状态目录中，不会自动遍历磁盘或读取项目业务文件。

## 记忆与方案如何维护

关联后，原 `agy_discussion_memory` 的新版本及 `agy_council_note(kind="plan")` 的新方案会保存到项目检查点。只有新的客户端版本才会更新项目，不会把旧讨论里的旧方案反复覆盖回来。源记录和实际发言来源保持不变。

也可以直接调用 `agy_project_update` 更新项目记忆或方案。记忆结构与任务记忆相同，但 `sources` 使用 **`discussion_id#message_id`** 字符串，避免不同讨论中的同号消息混淆：

```json
{
  "project_id": "demo-project",
  "expected_version": 3,
  "reason": "保留争议和需要验证的下一步",
  "memory": {
    "facts": [{"text": "已观察到的行为及其观察范围", "sources": ["实际讨论编号#1"]}],
    "disagreements": [{"text": "两条实现路径仍待比较", "sources": ["实际讨论编号#2", "实际讨论编号#3"]}],
    "positions": [{"participant": "claude", "view": "倾向先做较小修改", "reason": "迁移成本低，但性能仍需验证", "sources": ["实际讨论编号#3"]}],
    "next_steps": [{"text": "核对争议前提", "sources": ["实际讨论编号#2"]}]
  }
}
```

来源必须是该项目已关联讨论中成功、已公开的消息；观点必须引用对应参与者自己的发言。封存初判和失败输出不能作为项目事实来源。记忆整体4500 UTF-16单位，每节最多8项；完整方案4000单位并需 `plan_sources`。项目限定来源字符串也计入记忆长度，超限会拒绝，不静默裁剪。

新检查点包含原因和当前版本，不设32版等固定寿命。旧版可用 `agy_project_read(project_id, version=...)` 取回。模型运行期间不能替换共享上下文。若讨论已经保存而项目同步遇到本地 I/O 错误，可读取最新版本后用 `agy_project_update(capture_discussion_id=..., expected_version=..., reason=...)` 重做本地同步，不重跑模型。

## 暂停、恢复与完成

用 `agy_project_update` 提交当前版本和理由：

- `status="paused"`：暂停新请求；已经运行的调用不会因此取消，需取消时使用 `agy_cancel`。
- `status="active"`：明确恢复，原记忆、方案、观点、用量和历史都保留。
- `status="completed"`：明确完成；需先等待或取消活动请求。以后出现新工作时可明确恢复，不自动重新开启。

结束一场讨论的 `summary` 只归档该话题，不会结束项目。后续新建普通讨论并关联原项目即可继续；已归档的原讨论仍保持归档状态。

## 模型实际收到什么

后续请求完整携带当前项目记忆、项目当前方案及该模型在项目中的上一条公开成功观点；当前讨论的任务记忆、方案和角色机制保留。近期消息与待答问题按有界规则选取，跨讨论问题同样可以继续查找。`context.project_id`、`project_version`、`project_own_view_source` 和问题来源记录实际传入的项目版本及来源。

新话题的首轮仍不附带其他参与者的观点和分歧，只提供共同项目基线及自己的旧观点，并标记这是项目连续上下文。它不再冒充完全没看过项目的新评估。跨讨论来源用完整来源字符串说明，不要当作本场 `references` 的数字编号。

讨论提示词仍有32000 UTF-16单位上限；完整必要材料超限时，在预留请求前拒绝，要求明确缩小当前工作记忆。保存全部历史和每次把全部历史塞给模型是两件事。

## 长历史与检索

关联后的讨论使用内容摘要校验的不可变分页文件；每个文件仍限2MiB，发布新索引前先保存页面。原单文件记录在首次关联时保留精确本地备份。消息编号不变，不覆盖旧页面，不因超过160条或单文件2MiB而要求重建项目。

`agy_discussion_read` 默认返回最近100条；用 `message_offset`、`message_limit` 查看其他页。窗口提供“更早发言/较新发言/最新发言”。完整当前方案独立保留，翻页不会让它消失。任务记忆历史的公共响应只展示最近20版，`memory_version`、`budget_version` 是实际版本，不要用当前页数组长度推算期望版本。

`agy_project_read` 支持：

- 不传编号：列出当前状态目录中的项目。
- `participant="claude"`：取回该参与者近期观点轨迹、依据与实际渠道。
- `query="关键词"`：检索关联讨论中的公开正文摘录。
- `sources=["讨论编号#消息编号"]`：取回指定原始发言，核对摘要。
- `version=...`：读取原有项目检查点；使用量和关联讨论清单仍按当前历史查询，不冒充当时快照。

记录数量没有人为的项目寿命上限，仍受本机磁盘和资源条件约束。读请求有分页/数量限制；省略清单用范围和数量表示，完整原文保留。

## 升级与旧任务

未显式关联项目的旧任务继续执行原预算与存储规则，不自动扩大既有授权。关联才启用持续项目行为。客户端工具总数20；白名单需加入 `agy_project_read`、`agy_project_update`、`agy_project_link`，然后重开会话。

新的分页记录由0.9.0及后续兼容版本读取。旧安装和配置备份保留，但不要用旧程序直接解释新的分页索引；回退前先备份当前状态并保留新版本读取路径。升级不迁移登录资料，也不上传项目档案或真实对话。
